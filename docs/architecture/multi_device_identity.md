# Multi-Device Identity (Phase 16)

Addresses the gap Phase 14.5 found and Phase 15/15B deliberately left
open: a "Desktop Alice" and a "Browser Alice" are, today, two
completely unrelated cryptographic identities that happen to share a
username. This document designs the minimum secure foundation that
lets them be recognized as **the same account, on two authorized
devices**, without weakening anything about how a *peer* (a different
person) is verified.

Read together with [Security Architecture](security/security_architecture.md)
(the property-by-layer model this extends) and
[Threat Model](security/threat_model.md) (the attacker this must
remain safe against).

## 1–4: Existing architecture (audited, unchanged)

| Concept | Where it lives today | Notes |
|---|---|---|
| **Account identity** | `database/models/user.py::User.id` (UUID), authenticated via phone number + password → JWT (`auth/authentication_service.py`) | Already exists, already server-verified. Nothing here changes it. |
| **Login session** | `database/models/session.py::Session` | Ephemeral (per-login, expires, already has `device_name`/`platform`/`revoked` columns) -- ≠ a device's *cryptographic* identity, which must persist across many logins. Confirms this project's own naming convention for device metadata, reused below. |
| **Device's cryptographic identity** | One (ML-KEM-768, ML-DSA-65) keypair per `SecureKeyStore` (`storage/secure_key_store.py`), generated/persisted client-side, keyed by `user_id` but living in a local, unsynced file (`KEY_STORE_DIR`) | This is the actual gap: `user_id`-keyed but *device*-local. Two installs for the same account produce two unrelated keypairs. **Not changed by this phase** -- each device still generates and holds its own keys, never synced. |
| **Peer identity / trust** | `storage/secure_key_store.py`'s `PEER_STATE_UNVERIFIED`/`VERIFIED`/`KEY_CHANGED`, promoted only via `ClientSession.confirm_combined_peer_verification()` | **Not changed.** A peer is still verified per observed (username, fingerprint) pair -- see Section "Preserving peer verification" below. |
| **Combined identity fingerprint** | `crypto/key_manager.py::fingerprint_combined_identity(kem_pub, dsa_pub)` = SHA-256 of the two length-prefixed public keys | Already, precisely, a **device fingerprint** (it is keyed to one specific keypair, never to an account). Reused verbatim -- no new fingerprint primitive. |
| **ML-DSA identity/origin authentication** | `crypto/identity_protocol.py`, `crypto/message_protocol.py`, `crypto/group_key_protocol.py`, `crypto/session_key_protocol.py`, each with its own domain-separated purpose | Reused pattern (not the same purpose string) for the new device-management packets -- see Section 9. |
| **Server-side device-adjacent data** | `Session.device_name`/`platform` (ephemeral, per-login only) | No table today records a *persistent* device cryptographic identity. This phase adds one. |

**Terminology, kept strictly separate for the rest of this document**
(per this phase's own Step 6 requirement):
- **ACCOUNT ID** = `User.id`. One per person.
- **DEVICE ID** = a new UUID, generated by the device itself at
  enrollment time, naming one specific (KEM, ML-DSA) keypair.
- **DEVICE FINGERPRINT** = `fingerprint_combined_identity()` of that
  device's own two public keys -- unchanged primitive, new name for
  an existing concept.
- **PEER IDENTITY** = the existing, unmodified per-conversation trust
  concept: a local `ClientSession`'s VERIFIED/UNVERIFIED/KEY_CHANGED
  judgment about a specific (username, device fingerprint) pair it has
  observed. A device is a peer's device; "the account is the same" is
  never, by itself, treated as "the peer is verified."

## 3. New architecture

```
                    USER ACCOUNT (User.id)
                         |
          +--------------+--------------+
          |              |              |
      Desktop          Browser        (future) Mobile
      Device A         Device B        Device C
      KEM+DSA          KEM+DSA         KEM+DSA
      (local only)     (local only)    (local only)
          |              |              |
          +------ devices table (server) ------+
             device_id, user_id, public keys
             only, fingerprint, state,
             NEVER private keys
```

Each device keeps generating and holding its own keypair exactly as
today (`KeyManager`/`SecureKeyStore`, unmodified). What's new is a
**server-side `devices` table** recording which *public* device
identities are known for an account and whether each one is
`PENDING`, `AUTHORIZED`, or `REVOKED` -- plus a signed protocol for
moving a device between those states, so that transition is never the
server's unilateral decision.

## 4. Threat model additions

Extends [Threat Model](security/threat_model.md) with exactly one new
question: **can a party that controls the account's credentials (or
the relay) add a device the account's real owner never authorized?**

The server:
- **May**: authenticate account credentials (already does), store
  each device's *public* keys + fingerprint + state, relay
  enrollment/authorization/revocation packets, refuse to relay
  session/group-key material to/from a device it has recorded as
  `REVOKED` (an additional access-control layer, not the sole
  defense -- see below).
- **Must not** (and, per this design, cannot): possess any device's
  private key; mark a device `AUTHORIZED` on its own initiative;
  forge an authorization or revocation signature (it holds no
  device's private ML-DSA key); silently restore a revoked device's
  authorization.

**Defense in depth, explicit:** server-side revocation enforcement is
an additional, convenient control -- it is *not* the only thing
standing between a revoked device and a receiving client. Every
existing receiving-side check (`_peer_key_is_verified()`,
`_resolve_trusted_signing_key()` resolving only from the receiver's
own local state, signature verification before decapsulation) is
completely unmodified. A compromised server that ignored its own
`REVOKED` bookkeeping still could not make a receiving `ClientSession`
accept a signature it doesn't recognize as coming from a locally
`VERIFIED` peer identity.

## 5. Device enrollment flow

```
New device (e.g. Browser)                Existing account
        |                                  (already logged in)
        | 1. generate own (KEM, DSA)
        |    keypair locally (unchanged,
        |    automatic -- KeyManager)
        |
        | 2. build + self-sign a
        |    DeviceEnrollmentPayload
        |    (own device_id, own public
        |    keys, device_name/platform)
        v
   device_enroll_request  --(JWT-authenticated connection)-->  SERVER
                                                                  |
                                                    3. verify the self-
                                                    signature (proves
                                                    the requester holds
                                                    the claimed private
                                                    key -- NOT proof of
                                                    authorization, same
                                                    caveat identity_
                                                    protocol.py already
                                                    documents), store
                                                    row as PENDING
                                                    (bootstrap
                                                    exception: an
                                                    account's very
                                                    FIRST device is
                                                    auto-AUTHORIZED --
                                                    see Section 6)
```

A `PENDING` device can authenticate to the server (it has valid
account credentials) but is not yet `AUTHORIZED` -- it cannot enroll
further devices, and other clients treat it exactly like any other
not-yet-cryptographically-established peer until a human, on an
already-authorized device, explicitly authorizes it.

## 6. Device authorization flow

```
Existing AUTHORIZED device                          SERVER
        |
        | 1. device_list_request
        |------------------------------------------->|
        |<---- PENDING devices for this account ------|
        |    (device_id, fingerprint, name, platform)
        |
        | 2. human compares the fingerprint
        |    out-of-band (same UX as existing
        |    peer verification -- no new UI
        |    paradigm invented)
        |
        | 3. sign a DeviceAuthorizationPayload
        |    (account_id, target device_id,
        |    target device's fingerprint,
        |    authorizer's OWN device_id) with
        |    THIS device's own ML-DSA key
        |
        | device_authorize
        |------------------------------------------->|
                                          4. verify: (a) signature
                                          valid under the AUTHORIZING
                                          device's OWN already-
                                          AUTHORIZED public key on
                                          file, (b) target device_id
                                          exists and is PENDING,
                                          (c) target fingerprint in
                                          the signed payload matches
                                          the stored one (binds WHAT
                                          was actually verified, not
                                          just an ID) -> mark target
                                          AUTHORIZED
```

**Bootstrap case**: an account's first-ever device has no other
device to authorize it. It self-enrolls and the server marks it
`AUTHORIZED` immediately -- identical, in trust shape, to today's
implicit single-device model (the very first key a `SecureKeyStore`
ever generates is already unconditionally trusted for that install;
this phase makes that moment explicit and auditable rather than
introducing a new trust jump). Every device *after* the first requires
a real, existing `AUTHORIZED` device's signature.

## 7. Device revocation flow

Any `AUTHORIZED` device may sign a `DeviceRevocationPayload` (account
id, target device_id) with its own key. The server verifies the
signature is from a currently-`AUTHORIZED` device for that account and
marks the target `REVOKED`.

```
Account
  |
  +-- Desktop [AUTHORIZED]
  +-- Browser [AUTHORIZED]
  +-- Phone   [REVOKED]        <- cannot enroll further devices,
                                   cannot have new session/group-key
                                   material relayed to it (server-side
                                   check), and even if that check were
                                   bypassed, a receiver's own
                                   independent peer-verification state
                                   was never told to trust it in the
                                   first place
```

A revoked device's *existing* cryptographic material is not "wiped"
(the server never had its private keys to begin with) -- revocation
means the server stops treating it as a valid party for *new*
protocol operations, and other devices' own peer-verification state is
never automatically updated by revocation either (consistent with
"same account ≠ automatic peer trust", Section 11 below).

## 8. What this phase does NOT solve (explicitly out of scope)

- **Group-key re-sync when a device is added/removed.** A newly
  authorized device does not retroactively receive existing
  conversations' group keys in this phase -- that is the same "offline
  first contact" / key-redelivery machinery `client/session.py`
  already has for a *single* device reconnecting, extended to
  *multiple* devices is a follow-up, not attempted here to keep this
  slice reviewable.
- **Cross-device peer-verification propagation** (Alice verifies Bob
  on her desktop; her browser doesn't automatically inherit that
  verification). Deliberately not automatic -- see Section 11.
- Mobile clients (explicitly out of scope this phase).

## 9–20 answered inline above; explicit answers to the two device-vs-server questions

- **Can the server forge a device identity?** No -- it never holds any
  device's ML-DSA private key, so it cannot produce a signature that
  verifies under a device's public key, for either self-enrollment or
  authorization/revocation.
- **Can the server add an unauthorized device?** It can insert a
  `PENDING` row (that's what enrollment *is*), but cannot move it to
  `AUTHORIZED` itself -- only a signature from an already-`AUTHORIZED`
  device (or the bootstrap first-device case) does that.
- **Can one compromised device silently authorize another?** Only if
  that device was *already* `AUTHORIZED` -- exactly the same blast
  radius as today's single-device model (a compromised sole device
  already controls the account's crypto). This phase does not expand
  that blast radius; it makes multi-device authorization explicit
  and human-gated rather than silent.

## Preserving peer verification (Step 11 -- critical)

**Nothing about `VERIFIED`/`UNVERIFIED`/`KEY_CHANGED` changes.** In
particular, this phase does **not** implement anything resembling:

```
if username == same_username:
    automatically VERIFIED
```

Device enrollment/authorization is an **account-management**
operation between a user and their own devices. Peer verification
remains a **cross-account** trust decision between two different
people, made independently by each receiving `ClientSession` from its
own local state, exactly as today. The two are related only in that
both now use the same underlying combined-identity fingerprint
primitive -- never in that one grants the other.

## Database changes (Step 8)

New table `devices` (see `database/models/device.py`):

| Column | Type | Notes |
|---|---|---|
| `device_id` | UUID, PK | generated by the device itself |
| `user_id` | UUID, FK → `users.id` | account owner |
| `device_name` | String, nullable | e.g. "Bob's Laptop" -- matches `Session.device_name`'s existing convention |
| `platform` | String, nullable | matches `Session.platform`'s existing convention |
| `kem_public_key` | Text | base64 wire form, same representation `key_exchange`/`public_key` packets already use |
| `ml_dsa_public_key` | Text | base64 |
| `fingerprint` | String | `fingerprint_combined_identity()` output, indexed for lookup |
| `state` | String | `PENDING` / `AUTHORIZED` / `REVOKED` |
| `created_at`, `authorized_at`, `revoked_at` | DateTime, nullable except `created_at` | |
| `authorized_by_device_id` | UUID, nullable | which device authorized this one (NULL for the bootstrap first device) |

No private key column exists, and none is ever populated -- there is
no code path anywhere that could send one here (mirrors `server/
server_state.py`'s existing "never touches private material" property
for the in-memory `public_key` field).

## Protocol changes (Step 9)

New domain-separated purpose (its own module, `crypto/
device_protocol.py`, mirroring `crypto/identity_protocol.py`'s exact
`_coerce_to_bytes`/length-prefix convention): `DEVICE_PAYLOAD_PURPOSE
= b"qrscs-device-v1"`. Three canonical payload shapes, each binding
the operation type into the signed bytes so an enrollment signature
can never be replayed as an authorization or revocation:

- `canonical_device_enrollment_payload(username, device_id, kem_pub, dsa_pub, device_name, platform)`
- `canonical_device_authorization_payload(username, target_device_id, target_fingerprint, authorizer_device_id)`
- `canonical_device_revocation_payload(username, target_device_id, revoker_device_id)`

New packet types (`utils/protocol.py`, same flat-dict/request_id
convention as every existing packet): `device_enroll_request`/
`_result`, `device_list_request`/`_result`, `device_authorize`/
`_result`, `device_revoke`/`_result`. The account identity used
server-side is always `user.id` from the authenticated connection --
never a client-supplied field -- mirroring `handle_epoch_reservation_
request()`'s own established D4.1 convention exactly.

# Phase 16B — Hardening, Persistence, Revocation Enforcement

Closes three of Phase 16's own four documented limitations:
persistence across restarts, revocation enforcement reaching an actual
message-relay path, and (partially — see "Cross-device key
distribution" below) usability once a second device is authorized. Not
closed: a device-management GUI (still deliberately deferred).

## Persistent device identity (Step 2)

`device_id` is now persisted inside the SAME encrypted-at-rest file
`storage/secure_key_store.py` already keeps the device's KEM/ML-DSA
keypair in — not a second store. `SecureKeyStore.get_device_id()`/
`save_device_id()` mirror `get_own_kyber_keypair()`/
`save_own_kyber_keypair()`'s exact shape: absent-tolerant on read (a
store written before Phase 16B simply has no `device_id` section, read
as "never enrolled," not a malformed file), and refuses to silently
overwrite an already-persisted value on write. `ClientSession.
enroll_device()` now checks `key_store.get_device_id()` first and only
generates+persists a fresh UUID the very first time an installation
enrolls — proven end to end (not by directly assigning
`session.device_id`) by `test_restart_preserves_device_id_fingerprint_
and_avoids_duplicate_enrollment`, which authenticates a second, brand-
new `ClientSession` against the same on-disk key-store directory an
earlier "run" already wrote to.

## Device authentication binding (Step 3)

A new, fourth canonical payload/packet, `device_session_bind`
(`crypto/device_protocol.py::canonical_device_session_binding_
payload()`, `server/device_handler.py::handle_device_session_bind()`):
the connecting device signs `(username, device_id, a fresh client-
generated nonce)` with its own ML-DSA private key. The server verifies
against the device's already-on-file public key (never one in the
packet), confirms it belongs to this authenticated account and is
currently `AUTHORIZED`, and — only then — tags this **connection's**
`ServerState` entry with `device_id`. This is what later relay-path
checks (below) re-read on every subsequent packet; it is opt-in per
connection, not a change to `auth`/`login` itself, so every existing
(pre-Phase-16) client and test, which never calls this, is completely
unaffected.

Nonce note: a single client-generated nonce, not a full server-issued
challenge-response round trip. This connection is already TLS-
protected and JWT-authenticated before this step is reached, so the
realistic residual risk this narrows is an accidentally-resent stale
signature, not a network attacker (who cannot observe this exchange at
all). A server-issued challenge would close that residual gap further
and is recorded under Remaining Limitations.

## Revocation enforcement on relay paths (Step 4)

`server/device_handler.py::is_device_bound_and_authorized(state,
client_socket)` re-reads the LIVE database state on every call (never
a cached flag from bind time) and returns one of three values:
`None` (this connection never bound a device — every pre-Phase-16
client, deliberately treated as "not opted in," never a rejection),
`True` (bound and currently `AUTHORIZED`), or `False` (bound but
`PENDING`/`REVOKED`).

Wired into exactly one relay path this phase, chosen because it is the
specific gap Phase 16's own report flagged: `server/client_handler.py::
handle_group_key_distribution()` — checked on the **sender's** own
connection (first thing, before any other processing) and, separately,
on the **recipient's** connection immediately before relay. A
`REVOKED` device can therefore neither distribute new key material nor
have it delivered to it, proven against the real relay code (not a
unit test of the check function alone) by
`test_revoked_device_cannot_send_group_key_distribution`.

**Deliberately not extended this phase** to every other packet type
Step 4 listed (direct `session_key`, `direct_key_recovery_*`,
`group_key_rotation_*`, queued-message delivery) — touching each of
those is real, additional surface area on already-audited, security-
critical relay code, and Phase 16B's own efficiency rule weighed
against attempting all of them shallowly. Recorded honestly under
Remaining Limitations rather than silently left undone.

Defense in depth is unchanged: server-side enforcement is an
additional, convenient control, never the only one. A receiving
`ClientSession`'s own independent peer-verification/signature checks
were never told to trust a revoked device's key regardless of any
server-side bookkeeping.

## Cross-device key distribution (Step 5) — genuine scope finding

Writing `test_revoked_device_cannot_receive_group_key_distribution`'s
original form (Desktop-Alice sending directly to Browser-Alice, same
account, to exercise "deliver an existing group key to a newly
authorized device") surfaced a real, pre-existing architectural
constraint discovered during this phase, not introduced by it:
`ClientSession._resolve_direct_conversation_id()` explicitly refuses
to open a conversation with yourself (`"Cannot open a conversation
with yourself"`). This guard predates Phase 16 and exists for the
single-device-per-account model the rest of the system was built
around.

This means the originally-sketched design — reuse the existing
person-to-person `group_key_distribution` mechanism directly, address
a packet from "alice" to "alice" — does not work as-is, and this phase
did **not** work around it by weakening or removing that guard (out of
scope; it is unrelated, pre-existing, security-adjacent routing logic).
Genuine cross-device key re-sync (an authorized second device
retroactively receiving an *existing* conversation's group keys)
therefore remains **not implemented** — it needs either a dedicated,
non-conversation "device sync" packet/relay path (new, small, but real
work) or a deliberate, reviewed relaxation of the self-conversation
guard specifically for the authenticated-own-device case. Neither was
attempted this phase; this is the most significant remaining gap this
document records.

What **is** proven end to end this phase: revocation enforcement on
the *existing* group-key relay path works correctly using two
*different* accounts (Section "Revocation enforcement" above) — the
enforcement mechanism itself is real and tested; only its application
to same-account, cross-device sync specifically is blocked on the
finding above.

## Group-key epoch behavior (Step 6)

Not separately implemented this phase, as a direct consequence of
Step 5 above: with no cross-device re-sync mechanism yet, there is no
new code path that could receive a stale or unauthorized epoch for a
newly authorized device to get wrong. The *existing* epoch bounding
(`current_key_epoch`, `server/client_handler.py::handle_group_key_
distribution()`'s own `epoch > current_epoch` rejection) is untouched
and still applies to the one relay path this phase's device-state
enforcement was added to.

## Revocation semantics (Step 7)

Documented explicitly, per this phase's own instruction not to imply
otherwise: **revocation prevents future authorized access — it does
not, and cannot, cryptographically erase data a device already
received before revocation.** A revoked device retains whatever
plaintext/keys it already had; nothing in this system (or any system
where recipients hold their own decryption keys) can revoke that after
the fact. What revocation *does* guarantee, and what this phase proved:
a revoked device cannot reconnect as an authorized device
(`test_revoked_device_cannot_bind_session_on_reconnect`), cannot
authorize or revoke other devices
(`test_revoked_device_cannot_authorize_another`), and cannot send or
receive newly distributed group-key material on the one relay path
enforcement now covers
(`test_revoked_device_cannot_send_group_key_distribution`).

## Remaining limitations (honest, as of Phase 16B)

- **Cross-device key re-sync is not implemented** (Step 5/6) — the
  single biggest remaining gap; see above for the specific blocking
  finding.
- **Revocation enforcement covers one relay path** (`group_key_
  distribution`), not the full list Step 4 named (direct session keys,
  key recovery, group rotation, queued messages).
- **Session binding uses a client-generated nonce**, not a full
  server-issued challenge-response — a real but low-severity residual
  gap given the existing TLS+JWT preconditions (see "Device
  authentication binding" above).
- **No device-management GUI** — deliberate, per this phase's own
  instruction; a CLI/test-harness/API path is what was built and
  tested.
- Of the 19 named security cases (Step 12, A–S), the ones with a
  direct, real, passing test in `tests/test_device_identity.py` are:
  A (implicit, via successful enrollment), B, C/G, D, F/H (wrong-
  username-in-payload), F (modified device_id), G (modified
  fingerprint), H (replayed enrollment), I (revoked reconnect), J
  (revoked receiving group-key distribution), K (revoked sending),
  Q (structural, no private-key column). **Not individually tested**
  this phase: E (modified account identifier — not a literal wire
  field to tamper with, since the account is always server-resolved,
  not client-supplied, making this attack shape inapplicable as
  literally stated), L (stale group epoch — blocked on the Step 5/6
  finding above), M (tampered wrapped key on the device-sync path
  specifically — same block), N/O (replayed authorization/revocation —
  the domain-separated per-operation suffixes make cross-operation
  replay structurally impossible, proven by construction, but a same-
  operation replay-of-an-identical-valid-message was not separately
  tested), P (authorization signed by a device belonging to a
  different account — the `authorizer.user_id != user.id` check exists
  in `handle_device_authorize()` but has no dedicated test), R
  (duplicate fingerprint under a different device_id — no uniqueness
  constraint or test exists for this today; two devices with colliding
  fingerprints would currently both be allowed to enroll, which is a
  gap worth closing but was not discovered to matter for any proven
  attack this phase), S (server changing device state without a valid
  device signature — covered implicitly by the fact no code path sets
  `state = AUTHORIZED`/`REVOKED` outside the two signature-gated
  handlers, but has no dedicated adversarial test).

# Phase 16C — Cross-Device Key Synchronization

Closes the single biggest gap Phase 16B left open: an authorized
second device existed and was cryptographically authorized, but could
not use any *existing* conversation. This phase adds a dedicated
device-to-device key-delivery protocol -- proven against a real
server, real ML-KEM/ML-DSA/AES-256-GCM, and a real third-party peer
(Bob) who ends up genuinely exchanging encrypted messages with the
newly-synced device.

## Key synchronization threat model

Extends [Threat Model](security/threat_model.md) and this document's
own Phase 16 threat model with one more question: **can a party that
controls the account's credentials, or the relay, redirect key
material to a device the account owner did not intend, or extract it
from a device that should no longer have access?** The server:

- **May**: verify the sender's connection is a bound, `AUTHORIZED`
  device (re-checked live, never cached); look up the target device's
  *public* record (fingerprint, public keys, state); relay the opaque
  wrapped package to whichever connected socket is bound to that exact
  `device_id`.
- **Must not** (and cannot): decrypt the wrapped key (it is AES-256-GCM
  ciphertext under a key only ML-KEM decapsulation with the target's
  private key can recover); accept a client's bare claim of its own or
  another device's authorization state as proof; redirect a package to
  a device other than the one the sender's own signature named (Step
  8 -- the signature binds `target_device_id` *and*
  `target_fingerprint`, so the server substituting a different
  `device_id` at relay time would not change what was signed, but
  *would* fail verification on the receiving end, since the receiving
  device checks the same binding independently).

## Source-device authorization

`server/device_handler.py::is_device_bound_and_authorized()` (reused,
unchanged from Phase 16B) is checked first, before anything else, on
the SENDER's own connection -- a `PENDING` or `REVOKED` source cannot
send a sync package at all. Proven by
`test_sync_from_revoked_source_device_rejected`.

## Target-device binding

The target is never "the account" -- it is one specific `device_id`,
bound to a specific `target_fingerprint`, both explicit fields in the
signed payload (`crypto/device_protocol.py::
canonical_device_key_sync_payload()`). The server independently
verifies both against its own `Device` row (never trusting the
packet's claims) before relaying, and additionally verifies the target
belongs to the SAME account and is `AUTHORIZED`, never `PENDING`/
`REVOKED`. Proven by `test_sync_to_revoked_target_device_rejected`,
`test_sync_to_device_on_different_account_rejected`, and
`test_pending_target_device_cannot_receive_sync`.

## Encrypted key package format

No new cryptographic construction. `encapsulation`/`wrapped_key` are
produced by the EXACT SAME `KeyManager.wrap_key_for_member()`
ordinary group-key distribution already uses (ML-KEM encapsulation +
AES-256-GCM encryption of the key bytes) and consumed by the exact
same `KeyManager.unwrap_received_key()` on the receiving end. The only
new part is the ENVELOPE around it: a fourth canonical ML-DSA payload,
under its own top-level domain-separation purpose
(`DEVICE_KEY_SYNC_PAYLOAD_PURPOSE = b"qrscs-device-key-sync-v1"`,
genuinely separate from `DEVICE_PAYLOAD_PURPOSE`, not a suffix under
it), binding username, source device_id, target device_id, target
fingerprint, conversation_id, epoch, package_type, and the wrapped
material itself.

## Replay protection

The domain-separated purpose plus the bound `(conversation_id, epoch,
target_device_id)` tuple means a captured, genuine package cannot be
replayed against a different device, a different conversation, or
relabeled to a different epoch without invalidating the signature --
proven directly by `test_sync_with_tampered_epoch_after_signing_
rejected` (same technique as Phase 16's `test_modified_target_device_
id_after_signing_rejected`: take a genuine signature, mutate one bound
field, confirm rejection). A literal identical-package-replayed-twice
case was not separately tested this phase (see Remaining limitations).

## Epoch handling

The source device always reads its OWN `KeyManager.current_epoch()`
for the conversation being synced and binds that exact value into the
signature -- there is no code path that lets a caller supply an
arbitrary epoch independent of what the source device actually holds.
The pre-existing, unmodified `epoch > current_epoch` bound on the
ordinary `group_key_distribution` relay is untouched; this new relay
path does not reuse that specific check (it has no server-side notion
of a conversation's "reserved epoch" ceiling to compare against, since
device sync is not conversation-membership-scoped the way group
messaging is) -- recorded honestly under Remaining limitations rather
than implied to be covered.

## Server-as-untrusted-relay model

Unchanged and reconfirmed: the server never imports or touches
`crypto.aes`/`crypto.kyber`/`crypto.ml_dsa` decryption logic anywhere
in `server/device_handler.py::handle_device_key_sync()` -- it only
moves already-opaque bytes after checking signatures and states it can
verify without ever decrypting anything itself.

## Revocation semantics (for sync specifically)

Reconfirms Phase 16B's own honest statement: revocation prevents
*future* authorized sync (a revoked device can neither send nor
receive new sync packages -- both proven), but cannot retroactively
erase a key a device already received before revocation. A package
created before revocation but delivered after is not specially
detected as such this phase (see Remaining limitations) -- the
server's live state check happens at DELIVERY time (the target must be
`AUTHORIZED` *at relay time*), so a target revoked between package
creation and delivery is correctly rejected; a target revoked *after*
successful delivery keeps whatever it already received, honestly
consistent with "revocation is not cryptographic erasure."

## Persistence

Reuses `KeyManager.store_key()`'s existing `on_change` → `SecureKeyStore.
save()` persistence path completely unmodified -- a synced key is
persisted to disk exactly like any other conversation key already is,
with no new storage code. Proven end-to-end, using a genuinely fresh
`ClientSession` against the same on-disk store (never a manually
re-assigned key), by `test_restart_after_sync_preserves_key_and_can_
still_message`.

## A genuine, adjacent finding: third-party peer identity vs. same-
## account multi-device (and a real bug fix)

Writing the happy-path test surfaced that Bob (a genuine third party)
correctly flags Alice's second device as `KEY_CHANGED` the moment it
announces its own public key, because Bob already `VERIFIED` "the
account's username" against Alice's FIRST device's keys -- from Bob's
side, username is still the only peer-identity key, exactly as
before this phase, and this phase does not change that (see Step 16).
Reconciling "these two different device keys, under one username,
should both be recognizable to Bob" is a separate, harder problem this
phase does not attempt.

While proving Bob could correctly re-verify and then trust the newly-
synced device after this KEY_CHANGED, a real, pre-existing bug (not
introduced by this phase, latent since `confirm_combined_peer_
verification()` was written, never triggered by any prior test) was
found and fixed: confirming a peer's identity after a `KEY_CHANGED`
correctly persisted the new key to `SecureKeyStore` and cleared the
pending-change bookkeeping, but never updated the SESSION-LOCAL
`_observed_peer_signing_public_keys`/`_observed_peer_raw_public_keys`
caches `_resolve_trusted_signing_key()` checks first -- so the very
next signature verification for that peer would resolve the OLD, no-
longer-current key and incorrectly reject a genuine sender's messages.
The fix (two lines, `client/session.py::confirm_combined_peer_
verification()`) makes verification strictly MORE correct (fixes a
false rejection of legitimate traffic) and was confirmed to introduce
no regression against 55 existing peer-verification/first-contact/
key-verification tests, all still passing.

## Remaining limitations (honest, as of Phase 16C)

- **Group conversation sync (Step 12) was not attempted** this phase --
  direct-conversation sync alone already consumed the phase's full
  scope; the same `device_key_sync` packet/handler could plausibly
  carry a group key too (package_type already distinguishes "direct"
  from other kinds), but membership/authorization checks for a GROUP
  key specifically (is the source device's account actually a current
  member of that group?) were not designed or implemented.
- **No literal identical-package-replay test** (send the exact same

  was not specifically exercised.
- **A package created before revocation but delivered after** is
  handled correctly by construction (state is checked at delivery

- **No epoch ceiling check on the sync relay path** (unlike ordinary
  `group_key_distribution`'s `epoch > current_epoch` bound) -- the
  source device is trusted to report its own true current epoch
  honestly; there is no independent server-side upper bound for this
  packet type.
- **Third-party (non-account) recognition of multiple devices as one
  identity remains unsolved** -- see the finding above; Bob must
  re-verify each of Alice's devices individually, by design, not as an
  oversight.
- Of Step 15's 20 named cases (A-T), tests exist for: forged signature
  (A/analogous to earlier forgery tests), revoked source (G),
  revoked target (H), pending target (J), cross-account (K), tampered
  epoch (O). **Not individually tested** this phase: B/E (wrong
  source private key / wrong account — not a literal wire field to

  dedicated adversarial test simulates a malicious server).

## Phase 16D — Multi-Device Security Hardening + Device-Aware Peer Identity

Closes the most important architectural gap Phase 16C left open: the
peer-trust state machine (`VERIFIED`/`UNVERIFIED`/`KEY_CHANGED`,
`storage/secure_key_store.py`) was keyed purely by **username**. That
is correct for one device per account, but a genuine, previously-
unfixed problem for more than one: a real third party (Bob) who had
already `VERIFIED` Alice's Desktop would see Alice's Browser's
genuinely different ML-KEM/ML-DSA keypair — broadcast under the SAME
username — as `KEY_CHANGED` against Desktop's own slot, because both
devices collided into one trust record. This was flagged in Phase
16C's own report as a known, unsolved limitation. This phase solves it
— without weakening `KEY_CHANGED`, without auto-trusting a second
device, and without any new cryptographic primitive.

### Device-aware identity architecture

`client/session.py::_peer_identity_key(username, device_id=None)`
composes `f"{username}\x1f{device_id}"` when `device_id` is supplied,
or returns `username` unchanged when it is not. Every peer-trust-state
method (`get_peer_verification_state`, `_peer_key_is_verified`,
`_resolve_trusted_signing_key`, `_sender_trust_rejection_reason`,
`_is_verified_identity_mismatch`, `_flag_peer_identity_changed`,
`_record_peer_identity_observation`, `_currently_observed_peer_
identity`, `get_peer_fingerprint_for_verification`, `confirm_peer_
verification`, `confirm_combined_peer_verification`, `observe_peer_
identity`) gained an **optional trailing `device_id` parameter** and,
as its first step, routes its own `username` argument through this
helper.

This is deliberately the *smallest* change that achieves device-aware
trust: none of these methods were rewritten — each already treated its
`username` parameter as a fully opaque dict/store key (proven true
already by Phase 16C's device-peer trust, which passes a bare
`device_id` in as that same parameter with zero code changes needed).
Composing the key once, before the existing logic runs, is sufficient.

**Backward compatibility is structural, not incidental**: `device_id`
defaults to `None` everywhere, in which case `_peer_identity_key`
returns `username` completely unchanged — byte-for-byte identical
behavior to before this phase. Only a genuinely device-aware caller
(a session that has called `enroll_device()`, or a packet that
happens to carry a `device_id`/`sender_device_id` field) ever produces
a different, composite key. Every one of the 122 pre-16D regression
tests calls these methods with no `device_id` at all, and continues to
pass unmodified.

**Logical account identity vs. cryptographic device identity**: the
account (`username`/`User.id`) remains the *logical* identity a human
recognizes and a conversation is addressed to; a `(username,
device_id)` pair is the *cryptographic* identity a receiver actually
verifies a signature against. `KeyManager.public_keys` (the KEM
encryption-target cache used to encrypt a NEW session/group key TO
someone) deliberately stays account-level, single-slot, unchanged —
splitting that too would change which key `establish_session_key()`/
`wrap_key_for_member()` encrypt to for ordinary messaging, a
materially larger behavior change this phase's "smallest architecture
necessary" instruction does not call for. The dedicated
`device_key_sync` protocol (Phase 16C) already exists for the case
where a specific device needs to be an encryption target.

### Wire protocol changes (both additive, both optional)

- `create_public_key_packet(..., device_id=None)` — an identity
  broadcast now optionally carries the sending device's `device_id`.
  `ClientSession.send_public_key()` passes `self.device_id` (`None`
  until `enroll_device()` has resolved one). The receiving side
  (`_handle_signed_public_key()`) reads `packet.get("device_id")` and
  threads it through to every trust-state call listed above.
- `create_payload_packet(..., sender_device_id=None)` — an outgoing
  "chat" packet now optionally carries the sender's own `device_id`.
  Deliberately **not** part of `crypto/message_protocol.py::
  canonical_message_payload()`'s ML-DSA-signed fields — it is
  transport metadata only, used solely to select which `(username,
  device_id)` trust-state slot the receiver should resolve a
  verification key from. Because the ML-DSA signature is still checked
  against whatever key that selects, a tampered/forged `sender_
  device_id` can only ever cause a fail-closed rejection (wrong or
  missing key resolved), never a false acceptance — no cryptographic
  primitive changed, no new trust decision was added to the signature
  itself.

### A genuine finding this phase required to make the above actually work

The very first identity broadcast a session ever sends
(`send_public_key()`, called automatically right after login) fires
**before** `self.device_id` is ever resolved — `enroll_device()` is a
separate, later, explicit app-level action. For an account's *first*
device this is harmless (nothing else is `VERIFIED` yet to collide
with). For a *second* device connecting after the first is already
`VERIFIED` by a third party, that unavoidable first plain (`device_id`-
less) broadcast is genuinely, cryptographically **indistinguishable**
from an attacker substituting the first device's key — both look
exactly like a mismatch against the same plain-username `VERIFIED`
slot, and correctly produce `KEY_CHANGED`. This is not a bug in the
composite-key mechanism; it is why the mechanism exists at all.

Two changes close this properly:

1. `ClientSession.enroll_device()` now re-broadcasts this device's
   identity (calls `self.send_public_key()`) the moment `self.
   device_id` is first resolved (freshly generated, or loaded from the
   persisted key store) — so a device that enrolls shortly after
   connecting gets a second, device-scoped broadcast that establishes
   its OWN composite-key slot, without ever touching the first
   device's plain-slot record.
2. `server/server_state.py::set_public_key()` gained an optional
   `device_id` field (stored and relayed exactly like `signing_public_
   key`/`identity_signature` already are — the server never
   interprets or trusts it), and `server/client_handler.py` gained a
   **new dispatch branch** for a `key_exchange`/`public_key` packet
   arriving in the main receive loop (not just the one-time bootstrap
   read at connection setup) — before this phase, no legitimate client
   ever sent a second one, so nothing handled it; `enroll_device()`'s
   re-broadcast now does, every time. It reuses `state.set_public_
   key()`/`distribute_public_keys()` completely unchanged, a second
   time.

**Operational consequence, documented rather than hidden**: a
multi-device-aware client must call `enroll_device()` as part of its
normal startup/connection sequence — not defer it to an arbitrary
later user action — or a second device risks a spurious `KEY_CHANGED`
against a sibling device's already-`VERIFIED` slot the first time a
third party observes it. `tests/test_multi_device_peer_identity.py`
models this explicitly via a dedicated `_new_pre_enrolled_device_
session()` helper (enrolls immediately after `start_receiver()`, with
no separate plain broadcast at all) and documents exactly why in its
own docstring.

**A pre-existing test's assumption became outdated, and was updated,
not weakened**: `tests/test_public_key_identity_binding.py::
test_post_authentication_public_key_packet_does_not_rebind_identity`
asserted that a public-key packet arriving after connection setup was
always inert ("the loop has no handler for operation == public_key").
That was true before this phase and is no longer true by design. The
test was rewritten (renamed to `..._cannot_rebind_a_different_
identity`) to assert the property that actually matters and remains
fully intact: the sender's OWN key can now legitimately update, but an
attempted identity swap (claiming a DIFFERENT username than the
socket's own authenticated one) still fails completely — the victim's
stored key is never touched, and whatever the attacker's connection
causes to be relayed is still labelled with the attacker's own
authenticated username, never the claimed one. Verified directly:
`ServerState.set_public_key()` is keyed by socket, and `distribute_
public_keys()` labels the outgoing packet from the server's own JWT-
authenticated `client["username"]`, never from the packet's claimed
`username` field, which is not read at all.

### Multi-device trust model — proven third-party scenario

`tests/test_multi_device_peer_identity.py::test_bob_distinguishes_
alice_desktop_and_alice_browser_as_separate_devices` proves, using
only real `ClientSession`/network code (no internal dict
manipulation), the full scenario this phase's instructions specified:
Bob has already `VERIFIED` Alice Desktop; Alice Browser (second
device, same account) connects; Bob never conflates the two (Desktop
stays `VERIFIED` throughout, unconditionally); Browser is a distinct,
`UNVERIFIED`-until-confirmed identity; Bob keeps receiving genuine
Desktop messages the whole time; Bob separately verifies Browser and
then genuinely receives a real, ML-DSA-signed Browser message; a later
Browser key rotation produces `KEY_CHANGED` for Browser's slot only,
Desktop's independent slot completely unaffected, and Desktop remains
fully messagable throughout. Browser reaching Bob for message #8 goes
through the real, unmodified `device_key_sync` path (Desktop syncs its
existing Bob conversation's key to Browser) rather than an independent
`establish_session_key()` call — see the next subsection for why that
distinction matters.

### The conversation/epoch collision this phase discovered (and did not "fix" — it re-confirms why device_key_sync exists)

`conversation_id` for a direct conversation is resolved server-side
from the two **accounts'** (`User.id`) `user_id` pair, never from
device identity — so Alice's Desktop and Alice's Browser, sharing one
account, necessarily resolve to the exact same `conversation_id` with
Bob. An early draft of the multi-device peer-identity test had Browser
call `establish_session_key()` independently for that same
conversation — this collided with Desktop's already-established
epoch (observed directly: `duplicate_or_stale_key` then
`decryption_failure` rejections on Bob's side, followed by a second,
competing epoch being generated for the SAME conversation). This is
not a bug introduced by this phase; it is exactly the pre-existing
gap Phase 16C's `sync_conversation_key_to_device()` protocol already
exists to solve correctly — a second device of an already-conversing
account must **receive** the existing key via sync, never independently
re-establish a competing session for the same account-pair
conversation. The test was corrected to use the real sync path instead
of working around or hiding the collision.

### Exact replay semantics (Step 6)

Proven in `tests/test_device_key_sync_hardening.py`, using the real
`send_request()` path (a captured, genuinely-sent packet re-submitted
verbatim, never hand-assembled to simulate the wire):

- **Exact replay is a safe, idempotent no-op.** The identical signed
  package, delivered a second time (same session, and again after the
  target has fully disconnected and reconnected with device_id
  persisted), installs the identical key at the identical epoch with
  no change in outcome. This is not new replay-protection code — it
  falls directly out of `KeyManager.store_key()`'s pre-existing,
  unmodified guarantee ("never overwrites an existing epoch with a
  different key: if this exact epoch is already stored, this is a
  no-op" — already relied on by ordinary group-key rotation retries).
  This phase's contribution is proving that guarantee also covers the
  device_key_sync path.
- **A replay cannot be redirected to a different device.**
  `target_device_id`/`target_fingerprint` are bound into the ML-DSA
  signature; rewriting either after signing (simulating a malicious
  relay redirecting captured traffic to a third device) invalidates
  the signature and is rejected — proven directly, including
  confirming neither the original nor the redirected target ends up
  with the key.

No server-side nonce/sequence tracking was added — none was needed:
the properties above are exactly what a signed, epoch-keyed,
idempotent-per-epoch design already guarantees.

### Epoch / rollback protection (Step 7)

`KeyManager.store_key()`'s `_current_epoch[conversation_id] =
max(current, epoch)` is already strictly monotonic — no code path,
including device_key_sync's, can ever move it backward.
`tests/test_device_key_sync_hardening.py::
test_stale_epoch_sync_cannot_roll_back_already_advanced_local_epoch`
proves this holds through the real receive path: a target that has
already locally advanced to a later epoch (simulated, since group sync
is now implemented but this test isolates the epoch guarantee itself
without depending on it) accepts a genuinely-signed but stale
lower-epoch package — installing it at ITS OWN epoch slot, exactly as
a legitimate historical delivery should — while `current_epoch()`
stays at the higher value and that epoch's key is completely
undisturbed. A tampered-epoch-after-signing attempt (Phase 16C) and a
duplicate-current-epoch delivery (this phase's exact-replay test) are
both already covered. No independent server-side epoch ceiling was
added for this relay path (still an accepted, documented limitation —
see below): the source device's signature already proves it is an
`AUTHORIZED` sibling device of the account genuinely reporting its own
key state, not an untrusted party that could benefit from lying about
the epoch number.

### Revocation race / delivery ordering (Step 8)

`tests/test_device_key_sync_hardening.py::
test_revoking_source_after_legitimate_delivery_does_not_erase_
delivered_key` proves, honestly, the actual boundary: a device that
was `AUTHORIZED` when it synced a key, then revoked afterward, does
**not** retroactively lose the key material it already legitimately
delivered — revocation is prospective (blocks future syncs from the
now-revoked source, proven in the same test) never retroactive
erasure. This mirrors, and is consistent with, ordinary device
revocation's already-documented boundary elsewhere in this file. The
"target revoked before delivery arrives" and "source/target revoked
before it even attempts" cases were already proven in Phase 16C
(`test_sync_to_revoked_target_device_rejected`, `test_sync_from_
revoked_source_device_rejected`, `test_pending_target_device_cannot_
receive_sync`) — the server re-reads live DB state on every relay
attempt, never trusting a cached/client-claimed device state, so
"before" and "after" package creation make no difference to the
server-side check itself.

### Security negative-test matrix — updated status

Beyond Phase 16C's six (forged signature, revoked source, revoked

### Server authority audit (Step 10)

Re-read `server/device_handler.py::handle_device_key_sync()` end to
end against the full checklist: authenticated session (`user` is the
JWT-resolved ORM object, never packet-derived) — yes; sender's bound
device_id — yes (`is_device_bound_and_authorized()`, re-reads live DB
state, never cached); source device exists / belongs to the
authenticated account / is `AUTHORIZED` — yes (all three, via `Device
Repository.get_by_id()` on the SERVER's own bound-connection state,
never the packet); target device exists / belongs to the same account
/ is `AUTHORIZED` / fingerprint matches the stored record — yes, all
four, explicitly checked; target socket is genuinely bound to the
target device — yes (`_find_socket_for_bound_device()`, matches BOTH
`user_id` and `device_id` on the server's own live connection table,
never a claim). **One item is knowingly not enforced**: the server
does not verify that `conversation_id` refers to a real conversation
the authenticated account is a member of (unlike ordinary `group_key_
distribution`'s equivalent check). This was evaluated, not
overlooked: adding it would require every existing device_key_sync
test (Phase 16C's and this phase's) that intentionally uses a
freshly-minted, never-registered `conversation_id` for isolated
crypto-boundary testing to first register a real conversation,
substantial test churn for a check whose absence creates no reachable
attack surface — the server already treats `conversation_id` as an
opaque label (it never inspects or acts on the key contents), and the
recipient is unconditionally constrained to the SAME account's own
`AUTHORIZED` devices regardless of what `conversation_id` says.
Documented here as an accepted, deliberate gap rather than silently
left unaudited.

### Direct conversation synchronization

Unchanged from Phase 16C, reconfirmed by this phase's regression runs
(17/17 in `test_device_key_sync.py` + `test_device_key_sync_
hardening.py`) plus the new device-aware-identity and hardening tests
above, none of which touch the direct-sync code path itself.

### Group synchronization (Step 11)

**Implemented — with zero new code.** `sync_conversation_key_to_
device()`/`handle_device_key_sync()` (both client and server sides)
were already fully generic on `conversation_id` + `epoch` from Phase
16C's own design — `KeyManager` itself has no notion of "direct" vs.
"group" at all, and `package_type` was already opaque, relayed
metadata neither side branches on. `tests/test_group_device_key_
sync.py::test_newly_authorized_device_receives_existing_group_key_
and_messages_members` proves this directly: Alice Desktop creates a
real, server-authorized group with Bob and Charlie; Alice Browser is
newly authorized; Desktop calls `sync_conversation_key_to_device(...,
package_type="group")` — the exact same method, unmodified — and
Browser receives the group's real key via the real receive path,
decrypts a message Browser then sends, which both Bob and Charlie
genuinely decrypt, and Browser genuinely decrypts Bob's reply.

**Security, reused rather than reinvented**: a revoked source/target
device is rejected by the exact same checks direct sync already has
(not re-proven separately in the group test, to avoid duplicating
`test_device_key_sync.py`'s and `test_device_key_sync_hardening.py`'s
own coverage of that same code path). A device outside the group
receives nothing structurally — sync is addressed device-to-device
by `target_device_id`, never broadcast to a conversation's members, so
there is no group-membership check to bypass in the first place; the
existing `group_key_distribution` path (unrelated to device sync)
remains the only place ordinary group-membership enforcement lives,
and it is unchanged.

**Honest limitation carried forward**: because package_type is purely
descriptive, nothing currently stops a source device from mislabeling
a direct key as `"group"` or vice versa (the label itself is bound
into the signature — Step 9's "modified package_type" test proves a
MISMATCHED label fails, but a self-consistent, honestly-labeled-wrong
package would not be caught by this protocol; the receiving
`KeyManager.store_key()` does not know or care which conversation TYPE
a `conversation_id` names, only that its own local records exist or
don't). This was true before this phase too and is unaffected by it.

### SecureKeyStore audit (Step 12)

Reviewed the synchronized-key write path (`KeyManager.store_key()` ->
`SecureKeyStore._write()`, unchanged by this phase) and every log
statement on the device_key_sync send/receive paths (client and
server). Confirmed: keys are only ever written to the existing
encrypted-at-rest store, at the correct `(conversation_id, epoch)`
pair (proven by the restart test in `test_device_key_sync.py` and the
reconnect-replay test in `test_device_key_sync_hardening.py`); no
cross-device collision (each device's own `SecureKeyStore` file is
scoped to its own `KEY_STORE_DIR`, never shared); no stale-epoch
overwrite (Step 7, above). Grepped the full diff surface for
accidental logging of AES keys, ML-KEM/ML-DSA private keys, wrapped
plaintext, or decrypted conversation keys — every log line on these
paths logs only `conversation_id`, `epoch`, and `device_id` (all
non-secret identifiers), consistent with every other key-establishment
log line already in this codebase (`_report_security_rejection()`'s
own docstring: "never logs: signatures, encrypted/wrapped key
material, decrypted session keys..."). No changes were needed.

### Test-quality audit (Step 13)

Found and fixed one genuine issue: `tests/test_device_key_sync.py::
_mutually_verify_devices()` opened with `assert _wait_for(lambda: a.
key_manager.get_public_key(b.device_id) is None or True)` — a
predicate that evaluates to `True` unconditionally regardless of what
it inspects (`X is None or True` is always `True`), so `_wait_for`
returned on its very first check without ever actually waiting for or
proving anything. Removed rather than "fixed in place": the helper
reads key material directly from each session's own live `KeyManager`
object, never from anything observed over the wire, so there was
nothing genuine left to wait for once the vestigial check was
recognized as meaningless. A repo-wide grep for the same `or True`

## Phase 16E — Final Multi-Device Security Closure

Closes five of Phase 16D's six documented limitations (the sixth,
completing the full ~1,470-test suite, is inherently bounded by the
same Windows pytest resource-contention pattern documented since Phase
15B — not something a code change fixes).

### Server-side conversation authorization (Step 3)

`server/device_handler.py::handle_device_key_sync()` now additionally
verifies, from the server's own `ConversationMember` rows (via
`ConversationRepository.get_member_user_ids()` — the SAME method
`server/client_handler.py` already uses to authorize ordinary group
"chat"/`group_key_distribution` relay), that the AUTHENTICATED account
is a genuine member of `conversation_id` before relaying anything.
Previously, authorized-source + authorized-same-account-target was
treated as sufficient; it was not — either device could address a sync
packet to any conversation_id string, real or fabricated, since only
device state was ever validated. Since the target device is already
required (by Phase 16C's own, pre-existing check) to belong to the
SAME account as the source, one membership check on the authenticated
account covers both direct and group conversations without needing a
separate "is the target account a member" check.

**Test-suite consequence, handled directly rather than dodged**: this
made every Phase 16D test that used a fresh, never-registered
`str(uuid.uuid4())` conversation_id (used purely to isolate a
cryptographic-boundary check from conversation setup) fail against the
new membership requirement. Every affected test in
`tests/test_device_key_sync_hardening.py` was updated to use a real,
server-registered conversation (a new `_real_conversation_id()`
helper: a genuine peer + a real `establish_session_key()` round trip) —
never weakened, never given a bypass.

### Direct-conversation redirect protection (Step 4)

The new membership check alone does NOT defeat a redirect BETWEEN two
conversations the account is legitimately a member of — Alice really
can be in both Conversation A (with Bob) and Conversation B (with
Charlie). For that, the PRE-EXISTING protection already does the job:
`canonical_device_key_sync_payload()` binds `conversation_id` into the
ML-DSA signature, so a package genuinely signed for A's key cannot be
relabeled to B after signing without invalidating the signature.
`tests/test_conversation_redirect_security.py::
test_direct_conversation_a_key_cannot_be_relabeled_as_conversation_b`
proves this directly with TWO real, distinct, account-associated
conversations (a stronger case than Phase 16D's single-real-id
version) — rejected; B's own real key state, and both peers' identity
state, completely unaffected by the rejected attempt.

### Group-conversation redirect protection (Step 5)

Same protection, proven for two real groups (Group A: Alice/Bob/
Charlie; Group B: Alice/Dave/Eve) —
`test_group_a_key_cannot_be_relabeled_as_group_b`. Also re-confirmed
directly in this same test: a revoked target device is rejected for
group sync exactly as for direct sync (reuses the identical check, not
a separate implementation). "Target device belonging to a non-member
account" was evaluated and found already structurally impossible —
`device_key_sync`'s target must belong to the SAME account as the
source unconditionally (Phase 16C's own check), so there is no
reachable `target_device_id` on a non-member account to construct in
the first place; re-derived from Phase 16C's own `test_sync_to_
device_on_different_account_rejected` rather than duplicated.

**A genuine, orthogonal finding surfaced while building this test**:
if a second device of the SAME account is online DURING group
creation, it independently regenerates and distributes its OWN copy of
the group key —
`ClientSession.handle_group_create_result()` dispatches `if creator ==
self.username` (matched against the CONNECTION's own username, not
which socket actually created the group), so every one of that
account's simultaneously-connected sessions believes itself to be "the
creator." This is a real, pre-existing, orthogonal multi-device
behavior (not introduced by this phase, not touched by this phase's
scope) — worked around in the test by connecting the second device
only after group creation completes, exactly the scenario device_key_
sync exists to solve safely instead.

**Impact assessment (post-Phase-16E review)**: `_create_and_
distribute_group_key()` always generates a fresh `os.urandom(32)` key
with no "does this conversation already have one" check, so two
sessions of the same account both dispatching on `creator ==
self.username` really do produce two different random keys, each
stored and distributed independently. `KeyManager.store_key()`'s
same-epoch idempotency protects each RECEIVING client's OWN local
state (a member who receives both deliveries keeps only whichever
arrived first, never silently corrupted by the second), but does
nothing to reconcile the two ORIGINATING sessions with each other:
Desktop and Browser can each walk away believing a different key is
"the" group's real epoch-1 key. If the "losing" session (the one whose
delivery no member actually installed) later sends a group message
using its own, different local key, that message will fail to decrypt
for every member who installed the other key — a real, if narrow,
CORRECTNESS/reliability failure mode (undecryptable legitimate
messages), triggered only by the specific timing of a second device of
the same account being online at the exact moment a group is created.

This is **not a security vulnerability**: no unauthorized party ever
gains access to anything, no signature or trust check is bypassed, and
both candidate keys are still only ever delivered through the normal,
fully-authenticated `group_key_distribution` channel to genuinely
authorized members. It is also not silently unrecoverable: the
"losing" device can be brought back in sync at any time via the
already-proven, fully generic `sync_conversation_key_to_device()`
(Phase 16C/16D/16E) — it was not designed with this race in mind, but
it happens to already solve it, since it treats any conversation_id +
epoch identically regardless of how the local mismatch arose. There is
currently no AUTOMATIC trigger that detects and initiates that
corrective sync on its own.

**Decision**: left unfixed, deliberately, for this project's scope.
The real, correct fix (making `handle_group_create_result()`'s
"am I the creator" dispatch socket-specific rather than username-
matched) touches a load-bearing, unmodified-since-Phase-4 code path
shared by every group-creation flow in the codebase, for a benefit
limited to a narrow, uncommon timing window that the codebase's own
extensive group-messaging test suite never exercises (every existing
and Phase 16-series test connects a second device either well before
or well after group creation, never during it). Recorded here as a
known limitation / future improvement, not hidden, not silently
worked around outside of this document and the one test comment that
discovered it.

### Epoch validation and rollback protection (Step 6)

`Conversation.current_key_epoch` (bumped by `reserve_next_epoch()`,
the same server-persisted counter `establish_session_key()` and group
rotation already share) is the one authoritative source of "how far a
conversation has legitimately progressed." `handle_device_key_sync()`
now enforces, server-side, before any relay:

- `epoch` must be a plain positive integer (bool excluded explicitly,
  since it subclasses int) — mirrors `handle_group_key_distribution()`'s
  own, pre-existing, identical check exactly, reused rather than
  invented.
- `epoch` may not exceed `current_key_epoch` — same reasoning and same
  bound as that pre-existing check: without it, membership alone would
  let a member stamp a self-chosen, arbitrarily high epoch a receiver's
  own `max()`-based tracking could never recover from without a
  restart.

The RECEIVER's own monotonic `KeyManager.store_key()` protection
(proven in Phase 16D) remains fully in place, unchanged — defense in
depth for a relay that somehow bypasses the new server-side bound, not
replaced by it. Both layers now hold, exactly as this phase's own
instructions specified. Proven directly: negative epoch, non-integer
epoch, and an epoch exceeding the server's reserved ceiling are all
rejected before relay (`tests/test_epoch_and_domain_security.py`); an
epoch at the real reserved ceiling is accepted (no over-rejection of
legitimate traffic).

**Note on negative epochs specifically**: `canonical_device_key_sync_
payload()` packs `epoch` as an unsigned 4-byte integer
(`struct.pack(">I", ...)`), which itself raises for any negative
value — so no genuine client, however malicious, can even PRODUCE a
validly-signed negative-epoch package through the real signing path.
The test constructs the malformed packet directly (an unsigned/
arbitrary signature), exactly modeling the only way such a packet
could ever reach the wire: an attacker assembling raw bytes, never the
real client code.

### Package/domain separation (Step 7)

Audited whether `package_type` is security-sensitive: yes — it is
bound into `canonical_device_key_sync_payload()`'s ML-DSA signature
alongside every other field, so it was already NOT client-trustable
metadata (Phase 16D's `test_modified_package_type_after_signing_
rejected` already proved a mismatched label fails). This phase's
contribution is proving the BROADER Step 7 requirement directly rather
than merely asserting it: `crypto/device_protocol.py` domain-separates
every device-management operation by ML-DSA signing purpose
(`qrscs-device-v1` + a per-operation suffix for enroll/authorize/
revoke/session_bind; `qrscs-device-key-sync-v1`, a wholly separate
top-level purpose, for key sync). `tests/test_epoch_and_domain_
security.py` proves both directions of cross-operation replay fail: a
genuine ENROLLMENT signature cannot be resubmitted as a device_key_
sync's `sync_signature`, and a genuine key-sync signature cannot be
resubmitted to forge a device enrollment — ML-DSA signs exact bytes,
and the purpose prefix is baked into those bytes, so no second,
separate binding mechanism was needed or added.

**Known, accepted, honestly-documented residual gap**: nothing
prevents a source device from SELF-CONSISTENTLY mislabeling a direct
key as `"group"` (or vice versa) in a package it signs itself — the
label is bound into the signature (so a THIRD PARTY tampering with it
fails), but the server never sees the key content, so it cannot verify
the label matches the content's true origin. This is inherent to the
"server never sees plaintext" design and was true before this phase;
not fixable without breaking that property, so it is documented, not
silently left unaudited.

### Simultaneous-device race result (Step 8)

`tests/test_multi_device_concurrency.py::
test_simultaneous_sync_from_two_source_devices_to_a_third_is_safe`:
Desktop and Browser (both already legitimately holding the identical
conversation key) simultaneously sync it to Phone via two real Python
threads, each blocked on a real, separately-connected `ClientSession`'s
blocking `send_request()` — two genuinely concurrent connections
through the real server (the server already handles one thread per
connection; this exercises two of those simultaneously, never an
artificial bypass). Result: no deadlock (both threads provably
finished, not merely not-yet-observed-hanging), no crash (neither
raised), both requests independently accepted, and Phone ends up with
exactly the one correct key at exactly the one correct epoch —
`KeyManager.store_key()`'s pre-existing same-epoch idempotency is what
makes two concurrent, content-identical deliveries safe by
construction, never a race to "win." No server-side "only one
concurrent sync" lock exists or was needed.

## Phase 19.18 — Peer-verification persistence audit (per-client, not general)

The Phase 19.17 audit named a general "peer-trust/device-identity
session-locality limitation" without specifying which client(s) it
actually applies to. This phase re-derived the real, current answer by
reading each client's actual persistence path rather than assuming the
prior phrasing still applied uniformly, and it does not: **the gap is
Android-specific, not systemic.**

| Client | Peer verification (`VERIFIED`/`UNVERIFIED`/`KEY_CHANGED`) survives a restart? | Where |
|---|---|---|
| Desktop | **Yes.** | `client/session.py::confirm_peer_verification()`/`confirm_combined_peer_verification()` wrap `SecureKeyStore.verify_peer_fingerprint()` directly — there is no separate in-memory cache; `get_peer_verification_state()` reads `self.key_store.get_peer_verification(username)` live, every call. |
| Web | **Yes.** | `web/client/app.js`'s `_applyRestoredState()` restores `this.peers` (including each entry's `state`) from the browser's own IndexedDB-backed store on every reconnect/reload — proven live by `tests/test_web_persistence_reconnect.py::test_page_reload_restores_identity_and_trust_state` and re-confirmed this phase's own `test_web_settings_and_inbox.py` runs (`"Restored this browser's persisted identity"` in the real log). |
| Android | **No — session-only.** | `mobile/session.py::self.peers` is populated purely from live `observe_peer_identity()`/`observe_device_peer_identity()` wire events (`_upsert_peer_observation()`); `confirm_peer_verified()` (line ~656) sets `peer["state"] = PEER_STATE_VERIFIED` on that in-memory dict only — it never calls `self.key_store.verify_peer_fingerprint(...)`. `_unlock_key_store()` restores the owning device's own Kyber/signing keypair, `device_id`, and conversation keys from `SecureKeyStore`, but never restores `self.peers`. A previously-verified peer therefore reverts to `UNVERIFIED` the next time the Android app is relaunched, even though `SecureKeyStore` itself (same on-disk format Desktop/Android share) is fully capable of holding this state. |

**Classified D — acceptable final limitation, not C, because it is a
real shipping behavior, not merely an undocumented one; not A/B
because closing it safely requires Android source changes (Part 11's
full WSL2 rebuild + physical-device cycle) this phase's remaining
budget was better spent on the L-1 server-side security fix, Web
parity (L-5), and the real message-ordering defect found while
verifying Web history recovery (see the Final Report). Not deferred
for being "too much work" in the abstract — deferred because the
correct fix touches security-adjacent trust-persistence code on a
client this phase could not also take through Part 11 without
materially raising the risk of a rushed, under-tested change to
exactly the kind of logic this whole document exists to get right.**

**Why this is a usability gap, not a security hole**: every read of
verification state (`is_peer_verified()`/`_peer_key_is_verified()`,
Section "Preserving peer verification" above) is fail-closed by
construction — a reset-to-`UNVERIFIED` peer is treated exactly like a
peer never verified at all, which the whole rest of this document's
threat model already handles correctly (no automatic trust is ever
granted from an account/username match). The consequence of this gap
is strictly *more* re-verification friction after an Android restart,
never less scrutiny of an unverified key. No same-account
auto-trust, no weakened signature check, and no server-trusted
authorization state are involved.

**The safe fix path, for whoever closes this in a later phase** —
sketched, not implemented, so it does not silently bit-rot into a
vague future TODO: mirror Desktop's pattern exactly, in two additive
changes to `mobile/session.py`, neither of which touches signature
verification:
1. In `confirm_peer_verified()`/`confirm_device_peer_verified()`, once
   the in-memory state is set, additionally call `self.key_store.
   verify_peer_fingerprint(key, fingerprint, signing_public_key=...)`
   when `self.key_store` is available — exactly the write-through
   Desktop's `confirm_peer_verification()` already performs.
2. In `_upsert_peer_observation()` (or immediately after it, inside
   `observe_peer_identity()`/`observe_device_peer_identity()`), after
   recording a freshly-observed key, check `self.key_store.
   get_peer_verification(key)`: if a persisted entry exists with
   `state == PEER_STATE_VERIFIED` **and** its stored `fingerprint`
   equals the fingerprint just derived from the freshly-observed key,
   promote the new in-memory entry straight to `PEER_STATE_VERIFIED`;
   otherwise leave the existing `UNVERIFIED`/`KEY_CHANGED` logic
   untouched. This is the same "independently re-derive and compare,
   never blindly trust a stored claim" shape `confirm_peer_verification()`'s
   own hardening already uses on Desktop — a key that genuinely
   changed since last verification still correctly re-arms
   `KEY_CHANGED`, never silently re-trusts it.
Any implementation of this must ship with negative tests proving (a)
a changed key after restart is NOT auto-trusted, only an unchanged one
is, and (b) explicit verification persists across a simulated store
reload — and, per Part 11, a full APK rebuild, physical-device
install, and SHA-256/launch verification, since it touches
`mobile/session.py`.
