# ML-DSA-65 Benchmark

Documents the methodology and results of `benchmark/benchmark_ml_dsa.py`
(Phase 14.2), which measures this project's actual ML-DSA-65 (FIPS 204)
implementation — `crypto/ml_dsa.py::MLDSASigner`, backed by
`cryptography`'s native (Rust/OpenSSL) implementation. Nothing is
mocked or reimplemented for measurement; every timed call is a call
`MLDSASigner` itself makes. See
[Security Architecture](../architecture/security/security_architecture.md)
for where ML-DSA fits into the overall system.

## Methodology

- **Operations measured**: key generation (`MLDSASigner.generate_keys()`),
  signing (`MLDSASigner.sign()`), verification (`MLDSASigner.verify()`).
- **Message size**: 256 bytes — representative of this project's real
  signed payloads (`crypto/group_key_protocol.py`, `crypto/
  session_key_protocol.py`, `crypto/message_protocol.py`, `crypto/
  identity_protocol.py` all produce small, length-prefixed canonical
  encodings well under 1 KB). ML-DSA-65 cost is dominated by fixed
  lattice operations, not message length.
- **Iterations**: 200 for signing/verification, 100 for key generation
  (key generation is the most expensive of the three, so it gets a
  smaller, separate count — the same reasoning `benchmark_key_
  exchange.py`'s own `DEFAULT_KEYGEN_ITERATIONS` uses).
- **Warm-up**: 20 (signing/verification), 10 (key generation),
  untimed, run before any sample is collected.
- **Statistics**: mean, median, min, max, standard deviation, all in
  milliseconds — computed with Python's `statistics` module over
  `time.perf_counter()` samples.
- **Correctness gate**: every timed sample is independently verified
  correct immediately after being timed, but *outside* the timed
  window, so the correctness check itself never pollutes a
  measurement:
  - Key generation: exported public/private key lengths checked
    against ML-DSA-65's fixed sizes.
  - Signing: signature length checked against the fixed signature
    size, **and** the signature is independently re-verified with
    `MLDSASigner.verify()` before being accepted as a valid sample.
  - Verification: the boolean result is checked to actually be
    `True`.

  A single correctness failure aborts the whole benchmark run with a
  `RuntimeError` — the run either completes with every sample proven
  correct, or it does not report numbers at all.

## Results

Measured on the development machine, current working-tree benchmark
result (`benchmark/results/ml_dsa.json` — generated by the command
below, not yet committed):

| Operation | Mean (ms) | Median (ms) | Min (ms) | Max (ms) | Std Dev (ms) |
|-----------|-----------|--------------|----------|----------|--------------|
| Key Generation | 0.1405 | 0.1371 | 0.1353 | 0.3701 | 0.0238 |
| Signing | 0.6160 | 0.4904 | 0.2120 | 3.2830 | 0.4507 |
| Verification | 0.1354 | 0.1321 | 0.1296 | 0.2723 | 0.0150 |

**Sizes** (fixed by FIPS 204 — ML-DSA-65, identical for any conforming
implementation):

| Field | Size |
|---|---|
| Public key | 1952 bytes |
| Private key seed | 32 bytes |
| Signature | 3309 bytes |

**Environment**: Python 3.12.10, Windows-11-10.0.26200-SP0 (Intel64
Family 6 Model 151, AMD64), `cryptography` 49.0.0, native ML-DSA
implementation (`cryptography.hazmat.primitives.asymmetric.mldsa`).

## Timing results are environment-dependent — not universal

**These millisecond figures describe this specific machine, OS
scheduler, Python interpreter, and `cryptography` build on this one
run.** They are not a portable, machine-independent property of
ML-DSA-65 as an algorithm, and re-running the benchmark on different
hardware — or even the same hardware under different load — will
produce different numbers. What *is* fixed and reproducible anywhere
is the methodology (warm-up, iteration count, the statistics computed)
and the sizes table above, which are algorithm-intrinsic per FIPS 204.
Do not cite the timing numbers in this document as general ML-DSA-65
performance claims; cite them only as "this project's measured cost on
its development machine."

## Reproducing this benchmark

```bash
python -m benchmark.benchmark_ml_dsa
```

Writes a fresh `benchmark/results/ml_dsa.json` and prints the same
table shown above. Use `--iterations`/`--warmup`/`--keygen-iterations`/
`--keygen-warmup`/`--output` to adjust; see the script's own module
docstring (`benchmark/benchmark_ml_dsa.py`) for full usage.

## Relationship to the RSA/Kyber key-exchange benchmark

`benchmark/benchmark_key_exchange.py` (pre-existing, Phase 14.2's
predecessor infrastructure) measures the *key-establishment*
primitives (RSA-2048-OAEP, Kyber768/ML-KEM-768) this benchmark's
sibling to. ML-DSA-65 is the separate *signature* primitive that
authenticates the origin of every identity announcement, message, and
key-establishment packet those primitives produce — see
[Key Establishment Flow](../architecture/security/key_establishment_flow.md)
for how the two combine. The two benchmarks are intentionally kept
separate (one per primitive family) rather than merged, matching the
existing `benchmark/` directory's one-file-per-subject convention.
